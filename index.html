02 · 기존 방식

기존 LLM은 텍스트 어드벤처였다

판단 하나가 필요해도, LLM은 본업인 ‘다음 토큰 생성’을 멈출 수 없다. 매 턴 명령을 문장으로 타이핑하는 옛날 어드벤처 게임과 같다

① 입력

“이 문의를 어느 팀으로 보낼까?”

상황 묘사가 뜬다
② 토큰 생성

답을 글자 단위로 차례차례 쓴다

명령을 한 글자씩 친다
③ JSON 출력

{ team: “반품” } 같은 문자열을 만든다

문장이 완성된다
④ 파싱·검증

코드가 형식과 값이 맞는지 다시 본다

“그런 말은 모릅니다”
⑤ 재시도

형식이 깨지거나 애매하면 다시 부른다

처음부터 다시 친다

프로그램이 원한 건 “반품팀 61%” 하나인데, 매 턴 작은 작문 시험을 치른다

03 · 진짜 문제

LLM이 못해서가 아니라, 일이 안 맞는다

문장이 필요한 장면(대화 이벤트)과 고르기만 하면 되는 장면(전투 턴)이 섞여 있는데, 둘 다 같은 방식으로 처리하고 있었다

매 턴 작문을 시키면

  • 출력 토큰을 순서대로 생성해 지연이 생긴다
  • 긴 출력만큼 비용이 늘어난다
  • JSON 형식 이탈과 재시도를 관리해야 한다
  • “확신합니다”라는 말이 실제 확률은 아니다

그렇다고 오토배틀 매크로(규칙)만 쓰면

  • 현실의 애매한 표현을 다 담기 어렵다
  • 새 몬스터(새 사례)가 오면 매크로가 헛손질한다
  • 예외가 늘수록 조건문이 엉킨다
  • 빠르지만 유연하지 못하다

결정은 필요한데,
매크로는 딱딱하고 작문은 과하다

06 · 실제 사용처

어디에 쓰면 진짜 이득일까?

대사를 “작성”하는 곳보다, 같은 판단을 매 턴 “반복”하는 곳에서 빛난다

▶ 파티 배치

문의·모델 라우팅

문의를 반품·결제·배송팀으로, 작업을 작은 모델·큰 모델로 나눈다. 낮은 확신만 사람에게.

▶ 함정 감지

가드레일

위험한 셸 명령, 프롬프트 공격, 민감정보 가능성을 실행 전에 확률로 검사한다.

▶ NPC 행동

실시간 인터페이스

게임 NPC, 브라우저 다음 단계, UI 이벤트처럼 기다릴 수 없는 선택.

▶ 아이템 정리

대량 분류·재정렬

수천 개 문서의 주제, 관련성, 우선순위를 반복해서 판단한다.

09 · 오픈소스 용병

커맨드 메뉴는 집에서도 만든다

Jev와 같은 메뉴판(/v1/systemone)을 흉내 내는 오픈소스들. 메뉴는 같아도 레벨은 제각각이다

▶ Laya · 레벨 1 신입

421M·322M BERT, Apache-2.0

Jev와 같은 API, 맥북에서 돈다. 학습 없이는 공식 벤치마크 0.36(찍기 0.32). 레벨업(파인튜닝)이 전제.

▶ Ollama Nimble·Tev1 · 즉시 투입 용병

Qwen3.5-9B · 4B · 0.8B

Ollama 0.35+에서 바로 부른다. 영어 밖 언어 검증은 부족하다고 스스로 밝힌다.

▶ Jeeves · 생각하고 쏘는 마법사

고르기 전에 추론하는 9B

개발자 평가 93.5%(Jev 86.6%). 대신 중앙값 3.3초, 느릴 땐 17초. CUDA 전제.

▶ GLM 방식 · 전직

일반 LLM을 결정형으로

다음 토큰 확률만 읽어 Jev와 대등. 보기 이름을 동의어로 바꾸면 20%p 하락.

내 맥북 실측 · 2026-10-13 · Laya 다국어, 학습 없이

9/21 Jev와 같은 문구: 한국어 문의 분류 6/10(Jev 10/10) · 위험 명령 14개 중 Jev와 같은 판정 4개 · chmod 777 /etc/passwd를 최고 확률 0.88로 “허용”. 대신 한 건 약 23ms(모델 로딩 7초 별도).

테크 말로: 오픈소스가 따라 한 건 API 모양이다. 레벨 1 신입은 빠르지만, 내 데이터로 레벨업시키기 전엔 혼자 내보내지 않는다.
